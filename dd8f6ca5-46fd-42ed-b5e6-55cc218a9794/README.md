# اطلس — سامانه طراحی سیستم‌های ایمنی و آتش‌نشانی

نرم‌افزار تحت وب برای طراحی سیستم‌های اطفاء حریق پالایشگاهی: جانمایی تجهیزات،
زون‌بندی، محاسبات ورست‌کیس (NFPA 11/15/20)، طراحی لوله‌کشی و رینگ، و خروجی فنی.

---

## ۱. پیش‌نیازها

| ابزار | نسخه | چرا لازم است |
|-------|------|--------------|
| **Node.js** | ۲۰ یا بالاتر | نصب پکیج‌ها و اجرای Vite |
| **Bun** | ۱.۰ یا بالاتر | **اجرای بک‌اند الزامی است** — `server.tsx` روی `Bun.serve` اجرا می‌شود |
| Git (اختیاری) | — | فقط برای نسخه‌بندی |

نصب Bun:

```bash
# ویندوز (PowerShell)
powershell -c "irm bun.sh/install.ps1 | iex"

# مک / لینوکس
curl -fsSL https://bun.sh/install | bash
```

بررسی نصب: `bun --version`

> ⚠️ اگر Bun نداشته باشید، `npm run dev:full` فقط فرانت‌اند را بالا می‌آورد و
> API اجرا نمی‌شود؛ در نتیجه فهرست پروژه‌ها خالی می‌ماند.

## ۵. رفع اشکال

**صفحه سفید یا خطای «Something went wrong»**
۱. متن خطا در همان کادر قرمز روی صفحه نمایش داده می‌شود — با دکمه «Show details»
   می‌توانید stack کامل را ببینید. همان متن را برای پشتیبانی بفرستید.
۲. در کنسول مرورگر (F12) خطِ `[ShogoErrorBoundary]` اولین خطای واقعی را نشان می‌دهد.

**خطای «Element type is invalid … got: undefined» یا «Invalid hook call»**
تقریباً همیشه یعنی نصب پکیج‌ها ناقص/قدیمی است. بازنشانی کامل:

```bash
rm -rf node_modules package-lock.json bun.lock node_modules/.vite
npm install
npm run dev:full
```

<details>
<summary>ویندوز (PowerShell)</summary>

```powershell
Remove-Item -Recurse -Force node_modules, node_modules/.vite -ErrorAction SilentlyContinue
Remove-Item -Force package-lock.json, bun.lock -ErrorAction SilentlyContinue
npm install
npm run dev:full
```
</details>

**خطای ۴۰۴ روی `/api/...` یا «هنوز پروژه‌ای وجود ندارد»**
بک‌اند اجرا نشده است. `npm run dev:full` را بزنید (نه `npm run dev`).
بررسی سریع: `curl http://localhost:3001/api/projects` باید JSON برگرداند.

**پورت اشغال است**
اگر ۳۰۰۰ یا ۳۰۰۱ آزاد نیست، در `vite.config.ts` مقدار `server.port` و
در `package.json` متغیر `PORT` را تغییر دهید؛ هر دو باید هم‌راستا باشند
(proxy روی `localhost:3001` تنظیم شده است).

### موتور محاسبات بر پایه سند مشخصات

مرجع همهٔ محاسبات، سند `docs/ENGINE-SPEC-v1.2.docx` است. جداول آن با
`python3 scripts/gen-spec-tables.py` به `src/lib/spec/tables.generated.ts` تبدیل
می‌شوند — **خودکار و بایت‌به‌بایت**، نه بازنویسی دستی. برای تغییر هر جدول، سند را
عوض کنید و اسکریپت را دوباره اجرا کنید.

**یک منبع حقیقت.** زنجیره این است:

```
DOCX ──gen-spec-tables.py──▶ spec/tables.generated.ts
                                   │
                    spec/registry.ts ──▶ spec/engine.ts ──▶ هر ۲۰ خروجی §۴.۱
                                   │
                    calc/constants.ts ──▶ fireCalculations.ts ──▶ ۸ کامپوننت
```

هیچ عدد استانداردی در کد تایپ نشده: هر نرخ، زمان، حد و تعداد از جدول سند خوانده
می‌شود. اگر ردیفی از سند ناپدید شود، `calc/constants.ts` **خطا می‌دهد** و بی‌صدا به
عدد حافظه‌ای برنمی‌گردد (§۱۷ قاعدهٔ ۲: ممنوعیت پیش‌فرض تلویحی).

خروجی: هر ۲۰ مورد §۴.۱ (`OUT-001`…`OUT-020`) برای هر مخزن، همراه با کد وضعیت §۱۳،
شناسهٔ فرمول‌های §۴ که عدد را ساخته‌اند، و شناسهٔ جدول‌های مرجع §۳. قطر، ارتفاع و
سوخت از نقشه می‌آیند؛ صفر ورود دستی برای مقادیر استاندارد.

مقادیری که سند به عهدهٔ **تجهیز** گذاشته (پوشش نازل، منحنی پمپ، دبی مانیتور) در
`ENGINE_CONVENTIONS` اعلام شده‌اند و کنار هر خروجی با شناسهٔ ورودی جایگزینکننده
(`IN-0xx`) برچسب می‌خورند.

```bash
python3 scripts/gen-spec-tables.py   # بازتولید جداول از سند
bun scripts/spec-check.ts            # ۱۷۸ بررسی موتور استاندارد + اسکن برچسب‌های کهنه
bun scripts/calc-check.ts            # ۴۳۵ بررسی لایهٔ محاسبات و واسط
bun scripts/roof-basis-check.ts      # ۲۷ بررسی انتخاب مبنا برحسب نوع سقف
node scripts/watch-loop-check.mjs    # گارد حلقهٔ rebuild (watch set کرنل + بیکاری)
bash scripts/ui-check.sh scripts/roof-field-check.tsx h6   # فیلد «نوع سقف» در مشخصات تجهیزات
bash scripts/ui-check.sh scripts/spec-ui-check.tsx h3      # ماتریس §۴.۱ روی صفحه
```

## ۷.۲ نوع سقف مخزن (IN-008) — ورودی اجباری، نه پیش‌فرض

`IN-008` **بارِ محاسباتی** دارد: سناریوی §۳.۰A، مساحت حفاظت‌شده، نرخ و مدت تخلیه،
جدول تعداد خروجی، و از طریق جزء آبِ محلول فوم حتی دبی پمپ — همه از آن انتخاب می‌شوند.

| نوع سقف | جدول | نرخ | مساحت |
|---|---|---|---|
| سقف ثابت (Cone) | §۳.۱ | §۳.۲ — ۴.۱ L/min/m² | سطح مایع |
| شناور خارجی / داخلی | §۳.۴ (بالای سیل) · §۳.۵ (زیر سیل) | ۱۲.۲ L/min/m² | حلقهٔ آب‌بند |
| مواد آلوده / حوضچه | §۳.۸ | جدول §۳.۸ | هندسهٔ حوضچه |

اگر پروژه نوع سقف را ثبت نکرده باشد، موتور **متوقف می‌شود** و خروجی‌ها را با وضعیت
`INPUT_REQUIRED` برمی‌گرداند. جای این‌ها هیچ عددی چاپ نمی‌شود.

پیش از این، سه جا بی‌سدا «سقف ثابت» فرض می‌شد و تعداد فوم چمبر از **قطر تنها** با
جدول §۳.۱ حساب می‌شد — یعنی برای مخزن شناور هم طرح سقف ثابت داده می‌شد و برای مخزنی
که کسی توصیفش نکرده بود هم یک عدد چاپ می‌شد:

* `WorstCasePanel.elToTank` → `|| 'cone_roof'`
* `specProject.roofKindFor` → `: 'fixed'`
* `PropertyEditor` → فیلد «نوع سقف» در `realFields` مخزن نفتی **وجود نداشت**

و `validateTank` هم چون همان بالا مقدار گرفته بود، بررسی «نوع سقف» آن هیچ‌وقت اجرا نمی‌شد.

الان هرچه مصرف‌کنندهٔ عدد فوم است (پنل ورست‌کیس، مشخصات تجهیزات، پیشنهاد طرح،
فاز طراحی خودکار، جدول تجهیزات خروجی، و `calcWorstCase`) از یک جا می‌خواند:
خروجی `foam` موتور استاندارد. تفاوت‌شان فقط در این است که کدام پیکربندی سایت را
پاس می‌دهند.

## ۷.۱ تلهٔ rebuild بی‌پایان (مهم)

`vite build --watch` از watcher خودِ Rollup استفاده می‌کند، **نه** از watcher سرور dev.
یعنی `server.watch.ignored` در آن اثری ندارد. تنها جایی که کار می‌کند `build.watch` است:

```ts
build: {
  watch: {
    exclude: ['**/node_modules/**', '**/.shogo/**', '**/dist/**'],
    chokidar: { ignored: [/[/\\]\.shogo[/\\]/, /[/\\]dist[/\\]/, /[/\\]node_modules[/\\]/] },
  },
}
```

اگر این نباشد، build هر بار `.shogo/build-output.json` و
`.shogo/build-output-history.json` را می‌نویسد؛ watcher همان‌ها را می‌بیند و build
دوباره شروع می‌شود — ۶۰۰۰+ بار، و هر بار یک توست «Update available» روی صفحهٔ کاربر
می‌افتد که با هیچ رفرشی تمام نمی‌شود. `scripts/watch-loop-check.ts` این را قفل می‌کند.

## ۹. موتور محاسبات (دستورالعمل نهایی)

**منبع:** `src/lib/fire/` — `spec.ts` (گروه‌ها، سناریوها، ثابت‌ها) و
`engine.ts` (محاسبه). این ماژول **فقط** بر پایهٔ دستورالعمل نهایی نوشته شده
است؛ هیچ استاندارد، ضریب، فرض، قابلیت یا خروجی بیرون از آن اضافه نشده.

**ورودی‌ها:** قطر و ارتفاع مخزن · نوع ماده نفتی · نوع سقف · سناریوی اطفا ·
عرض ناحیه سیل · مساحت باندوال (مستقیم یا طول×عرض) · مدل و ظرفیت مانیتور/هوزدستی ·
تجهیزات مجاور و درصد کولینگ هرکدام · داده‌های هیدرولیکی سایت · فاصله رینگ و
اسپرینکلر در دو حالت.

**گروه‌ها (§۲):** Alpha = بنزین موتور، نفت سفید، نفت خام ترش، نفت خام سبک،
مواد آلوده نفتی · Beta = نفت کوره، نفت خام سنگین، گازوئیل.

**سناریوها:** سقف ثابت → فوم‌چمبر (4.1) / مانیتور یا هوزدستی (6.5) ·
شناور خارجی → غرق‌شدن سقف (4.1) / بالای سیل (12.2, 20min) / زیر سیل (20.4, 10min) ·
شناور داخلی → سیل (12.2, 20min). کولینگ 4.1 L/min/m² روی π·D·H به مدت 240 دقیقه.
ضریب اطمینان 1.2 **یک‌بار** روی جمع‌های طراحی.

**خروجی:** دقیقاً همان **۱۷ مورد** §۱۲ — نه یکی بیشتر. هر ردیف ارزش، واحد،
وضعیت، و «مبنای محاسبه» (زنجیرهٔ جانشینی + شمارهٔ بند) را نشان می‌دهد.

**هیچ‌چیز حدس زده نمی‌شود.** اگر داده‌ای نباشد یا دستورالعمل فرمولی برای آن
بخش تعریف نکرده باشد، آن خروجی «داده کافی نیست» می‌گیرد و فقط ورودی‌های
ضروریِ مفقود نام برده می‌شوند؛ مقدار جایگزین ساخته نمی‌شود. سه حالت وضعیت:
`محاسبه‌شده` · `داده کافی نیست` · `در مرجع تعریف نشده` (مثل مشخصات جوکی‌پمپ).
ترکیب ناممکن سقف+سناریو رد می‌شود، نه آنکه به نزدیک‌ترین حالت مجاز خم شود.

**تست:**
```bash
bun scripts/fire-check.ts                     # ۸۱ بررسی موتور
bash scripts/ui-check.sh scripts/fire-ui-check.tsx fireui   # ۳۱ بررسی UI
```

## ۱۱. کدام سیستم اطفا روی کدام مخزن مجاز است

یک مخزن **سقف ثابت** فوم‌دم ندارد — فوم‌دم فقط روی سقف شناور معنا دارد. و
**حوضچه** (مواد آلوده / Dike & Spill) مخزن نیست که فوم‌چمبر، کولینگ یا فومینگ
بگیرد؛ با مانیتور یا هوزدستی اطفا می‌شود.

قاعده در یک جا زندگی می‌کند: `src/lib/fireSystemRules.ts`.

| سقف | کولینگ | فوم‌چمبر | فوم‌دم | فوم داخلی | هوزدستی |
|---|---|---|---|---|---|
| ثابت | ✅ | ✅ | 🚫 | ✅ | ✅ |
| شناور خارجی | ✅ | ✅ | ✅ | 🚫 | 🚫 |
| شناور داخلی | ✅ | ✅ | ✅ | 🚫 | 🚫 |
| حوضچه | 🚫 | 🚫 | 🚫 | 🚫 | ✅ |

**سقف شناور با فوم‌چمبر اطفا می‌شود، نه با مانیتور و شیلنگ دستی** — همین قاعده در
موتور محاسبه هم اعمال می‌شود: خروجی ۴ (مانیتور/هوزدستی) روی سقف شناور «بی‌ارتباط با
سناریو» می‌گیرد و خروجی ۳ (دبی هر فوم‌چمبر) محاسبه می‌شود. ارتفاع فوم‌دم هم از برنامه
حذف شده است؛ این سیستم فقط به‌عنوان «نصب‌شده» ثبت می‌شود.

- سیستم غیرمجاز **پنهان نمی‌شود**؛ خاکستری و غیرقابل‌تیک می‌شود، با دلیل.
- با تغییر نوع سقف، فلگ‌های نامجاز **خودکار پاک** می‌شوند
  (`sanitizeFireSystems`) — طرحی که فوم‌دم داشت و سقفش ثابت شد، دام را از دست می‌دهد.
- خواننده‌ها (نشان نقشه، BOM، گزارش) از `isFireSystemActive` می‌خوانند، پس فلگ
  باقی‌مانده در یک طرح ذخیره‌شده هم شمرده نمی‌شود.
- پیمایشگر توکن سقف هم همین‌جاست، پس `specProject` و پنل نمی‌توانند اختلاف پیدا کنند.

**تست:**
```bash
bun scripts/fire-rules-check.ts                                   # ۵۸ بررسی قاعده
bash scripts/ui-check.sh scripts/fire-system-ui-check.tsx fireui  # ۳۲ بررسی روی پنل واقعی
```

## ۱۲. فرمول‌ها فقط در بخش خروجی

پنل‌ها **فقط نتیجه** را نشان می‌دهند. زنجیرهٔ جانشینی («مبنای محاسبه») و شناسهٔ بند،
فقط زیر هر خروجی در بخش «خروجی‌های محاسبه» باز می‌شود.

پیش از این، هر سیستم اطفا فرمول خودش را داخل پنل چاپ می‌کرد؛ همان متن‌ها با موتور
واگرا شدند و یک بار عدد بازنشسته را به کاربر نشان دادند. حالا فقط یک جا هست.

**تست:** `bash scripts/ui-check.sh scripts/roof-field-check.tsx roof` (۹ بررسی — پنل نباید `T3.x` چاپ کند)

## ۱۳. دوزبانه (فارسی / انگلیسی)

دو زبان **کامل از هم جدا** هستند: هر رشتهٔ دیدنی از `src/lib/i18n.tsx` می‌آید و
جهت سند با زبان عوض می‌شود (RTL ↔ LTR). کلید تغییر زبان گوشهٔ همهٔ صفحه‌هاست
(`data-lang-toggle`).

- توکن‌های فنی لاتین (`Direct Spray`، `Rundown`، `Alpha`، `Beta`، نمادهای واحد) در
  هر دو زبان لاتین می‌مانند — نام‌اند، نه متن.
- موتور محاسبه **فقط فارسی** می‌نویسد (واژگان خودِ سند است)؛ صفحه‌ها با `id` ترجمه
  می‌کنند. متن موتور (فهرست «داده‌های لازم»، یادداشت‌ها، برچسب شکل‌ها) با نگاشت
  `translateEngineText` ترجمه می‌شود — شامل متن‌های پویا با عدد داخلشان.
- زبان در `localStorage` (کلید `atlas_lang`) می‌ماند.

مسیرها: `src/lib/i18n.tsx` · `src/components/LanguageToggle.tsx` (و مصرف در
`App.tsx`، `FireCalcScreen.tsx`، `Dashboard.tsx`، `LandingPage.tsx`).

**تست:** `bash scripts/ui-check.sh scripts/i18n-check.tsx i18n` (۲۳ بررسی — از جمله:
هیچ متن فارسی‌ای پس از محاسبه در بخش خروجی نمی‌ماند)

## ۱۴. محاسبهٔ ناحیه ریم سیل (`D − W`)

مساحت ریم سیل اختلاف مساحت سطح با قطر `D` و سطح با قطر `D − W` است:

```
A = π/4 × (D² − (D − W)²)
```

`W` پیش‌فرض ۰.۶ متر است و در مخازن سقف شناور به‌صورت دستی وارد می‌شود. (پیش از این
قطر داخلی `D − 2W` گرفته می‌شد که مساحت را دو برابر می‌کرد.)

## ۱۵. کولینگ: هر دو حالت جداگانه

خروجی ۱۷ هم **Direct Spray** و هم **Rundown** را با تعداد رینگ و تعداد آب‌پاش نشان
می‌دهد تا طراح انتخاب کند. هیچ‌کدام جایگزین دیگری نیست.

## ۱۶. دبی پمپ و انتخاب خودکار سایز لوله

دبی پمپ = جمع **همهٔ** مصرف‌کننده‌های انتخابی (فوم + کولینگ + مانیتور/هوزدستی) ×
ضریب اطمینان ۲۰٪. سپس روی همان دبی و با هیزن–ویلیامز، سایز لوله انتخاب می‌شود:

- اگر قطر وارد شده باشد، همان استفاده و سرعتش گزارش می‌شود.
- اگر خالی بماند، **کوچک‌ترین** قطر کتابخانه‌ای که سرعت را زیر `MAX_VELOCITY_M_S`
  (۵ m/s، `src/lib/fire/spec.ts`) نگه دارد انتخاب می‌شود.
- سایز، سرعت، افت اصطکاکی و هد کل به‌عنوان شکل‌های خروجی ۱۲ نمایش داده می‌شوند.
